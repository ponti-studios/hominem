What happens when the app asks a model something

Same system as the diagrams below, told as what it resembles: ordering at a counter where the kitchen calls out each word as it's cooked, and keeps a running order book so nothing gets lost.

  1. You place an order. Typing a message and hitting send is like walking up to a counter and asking for something — "Can you summarize this contract?"

  2. The counter writes it down before doing anything else. The app's server logs your request permanently first, then hands it to the kitchen — so a crash a second later can't make your order vanish.

  3. The kitchen calls out words as they're cooked, not all at once. That's why the answer appears to type itself: you're seeing it arrive a few words at a time instead of waiting for the whole thing to be plated.

  4. Every word gets written into the order book as it goes out. If your phone drops the connection mid-answer, reopening the chat doesn't start over — it asks the order book "what did I miss after word 42?" and picks up there.

  5. If you cancel, the kitchen finishes its current step first. It checks "has this been cancelled?" between steps rather than dropping a spoon mid-stir — so you never get a sentence torn off for no reason.

Everything past this point is the same story again, in the vocabulary the code actually uses — the counter is the API route, the kitchen is the model provider and tool registry, and the order book is the Postgres event log.

Still one loop, several reducer functions

Text deltas, tool calls, retries, and cancellation all flow through the same reduce → command → effect → input cycle — reduceGeneration() just dispatches to a distinct pure function per input type now, instead of one big switch.

Event log and projection are separate tables

app.chatGenerationEvents is the append-only source of truth; app.chatGenerationRuns is a denormalized status projection folded from it — a formal event-sourcing split the old diagram didn't have.

Tool results are idempotency-cached

app.chatGenerationToolEffects (or a Redis-backed equivalent) keys tool results by (generationId, idempotencyKey, toolName) so a retried effect can't run a side-effecting tool twice.
